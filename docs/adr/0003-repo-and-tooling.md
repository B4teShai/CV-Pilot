# ADR-0003: Repository, packaging and quality tooling

**Status:** accepted
**Date:** 2026-10-14

## Context

CV-Pilot is an installable Python package that must work on CPU-only laptops and CI
runners, be easy to contribute to, and keep a strict quality bar from the first commit. It
is developed alongside a sibling project with the same conventions.

## Options considered

### Option A: monorepo with both projects

Trade-offs: one CI, shared tooling; but coupled release cycles, one issue tracker for two
products, and a heavier clone for users of one package.

### Option B: independent repositories with mirrored conventions

Trade-offs: each project releases and is adopted on its own; conventions can drift unless
they are generated from one source.

### Packaging: setuptools vs hatchling; pip-tools vs uv

Trade-offs: hatchling has a smaller configuration surface and native `src/` support; `uv`
gives a committed lockfile and fast, reproducible installs in CI.

## Decision

Option B, independent repositories. Conventions are generated from a shared template so
they stay mirrored by construction.

- Python ≥ 3.10; `src/` layout; hatchling build backend; `uv` with a committed `uv.lock`;
  CI installs with `uv sync --locked`.
- Core runtime dependencies: `typer`, `click`, `pydantic` (v2), `structlog`, `pyarrow` (Parquet
  metric files, imported lazily; added with the run store per
  [ADR-0005](0005-run-store.md)), `numpy` (the eval engine's array math, BSD-3-Clause, about 25 MB
  installed; added with the eval engine, see the note below). Anything heavier
  (PyTorch, Polars, FastAPI, database drivers) arrives only behind an optional extra. The
  core wheel stays CPU-only and torch-free.
- Quality gate on every push: `ruff check`, `ruff format --check`, `mypy --strict` on
  `src/`, `pytest` with coverage ≥ 85 %, on Python 3.10 to 3.13.
- Diagrams: `.excalidraw` sources plus PNG with the scene embedded, generated by scripts
  from the workspace toolchain. Outside the workspace the `.excalidraw` files are edited
  directly.

## Eval engine dependencies

`numpy` joins the core with `core/metrics.py` and `eval/`: IoU matrices, greedy matching and
precision-recall curves are array code, and per-item Python loops over 100 000 detections miss
the throughput budget in [../architecture/01-overview.md](../architecture/01-overview.md). The
domain layer may import it ([ADR-0004](0004-layering-and-dependency-rule.md)). It is imported at
module top level by `core/metrics.py`, `core/confusion.py`, `eval/` and `store/tables.py`
(`core/schema.py` and `core/hashing.py` import it lazily); the CLI imports those lazily inside
commands, so `cvpilot --version` stays within its startup budget. `pycocotools` is a dev-only
dependency for the parity tests and is never imported from `src/`. The architecture documents
also name `faster-coco-eval` as a core dependency; it is not added: the engine computes COCO
metrics itself (verified against pycocotools to the last digit on randomized sets), which
avoids a compiled dependency and a second implementation to keep in step.

## Consequences

- Adding a core dependency is a visible, reviewed change to this ADR and `pyproject.toml`.
- Contributors need `uv`; nothing else beyond a supported Python.
- The two projects share no code at runtime; shared contracts (for example the dataset
  version hash) are documented, not imported.
